# V7 IPTV - subtitles, stability, network reliability and security round (2026-11-07)

Branch `feature/v7-next-features`. Hardware checklist: `docs/checkpoint-v7-stability.txt`. Everything below was found
and verified on Linux; nothing here was run on a PS4 yet.

## 1. GitHub issue #1 - "arabic subtitles lag"

**Reproduced with the console's subtitle stack** (`tests/subtitles`): FreeType 2.10.1, FriBidi 1.0.4 and libass 0.14.0
built from source in the configuration of PacBrew's PS4 packages (no fontconfig, no HarfBuzz, C rasterizer - checked
against the objects in the sysroot's `libass.a`), driven frame by frame the way libmpv 0.34.1's `sd_ass` drives it,
with every libass message replayed through the app's own log path.

**Root cause.** mpv hands libass `<config-dir>/subfont.ttf` as its only font. v0.3.0 copied Inter SemiBold there,
which has no Arabic, Hebrew or bidi-mark (U+200E / U+200F, U+202A-202E) glyphs. Without a font provider, libass's
only fallback is that same file, so for every Arabic letter of every rendered frame libass:

- searched for a font again (`ass_font_select`), re-checked every charmap, and
- emitted 3-6 log lines ("Glyph 0x627 not found, selecting one more font", "fontselect: Using default font",
  "Glyph ... not found in font"). The app asks mpv for its verbose log, and the warning / info lines among them were
  each redacted, written to `log.txt` with `fflush`, and mirrored with `sceKernelDebugOutText` - **on the main
  thread, inside `mpv_render_context_render`** (the render API runs libass on the caller's thread). Warnings were
  also exempt from the 16 MB log cap.

Measured over two minutes at 30 fps with identical timing / structure: Latin control 2 log lines and 0.018 ms of
libass time per frame; Arabic 268,670 log lines (~83 per frame, 20 MB of log) and 0.37 ms per frame, with every
Arabic letter drawn as a missing-glyph box. Long Arabic lines: 4,992,122 lines in 5 minutes. The subtitle timing
itself was correct in every fixture (an event is drawn exactly while it is due): the "lag" is the per-frame work on
the render thread, not a timing offset. libass 0.14.0 also leaves the face id of that fallback uninitialised
(`ass_font_select`, default-path branch; the PS4 `add_face` compares the unset stack slot), so a second font in
`~~/fonts` cannot be relied on as a fallback.

**Fix.**
- `third_party/fonts-subtitles/V7Subtitles.ttf` (generated by `scripts/make-subtitle-font.py`, byte-reproducible):
  Inter SemiBold with every glyph, metric, kerning / layout table and hinting program unchanged, plus 527 code points
  from DejaVu Sans - Arabic, Arabic presentation forms A / B (what FriBidi shapes into without HarfBuzz), Persian /
  Urdu letters, Hebrew, bidi format characters - and empty glyphs for U+061C / U+2066-2069. One face covers
  everything, so libass never falls back. Latin subtitles are pixel-identical (all 2,937 Inter glyphs verified).
  Licence: OFL 1.1 (DejaVu's Arabic / Hebrew are public-domain DejaVu additions; the generator refuses any glyph
  DejaVu encodes outside those blocks, i.e. never a Bitstream Vera / Arev glyph).
- `player/subtitle_font`: installs it as `subfont.ttf` (marker file: a replaced font of the same size is copied too;
  packages without it fall back to Inter as before).
- `player/mpv_log_filter`: font-search lines are never written after the first six of a playback; one summary
  ("the subtitle font has no glyph for N character(s): U+...") every 30 s and at the end. Any other mpv burst is
  limited to 60 lines a second ("N mpv log line(s) not written"). Parsing for errors is unchanged.
- Diagnostics for hardware: per playback session, the main-thread render time (mean / max / > 33 ms) with and without
  subtitles on screen, the selected subtitle track, whether right-to-left text was shown (never the text itself).

Result: every Arabic / Hebrew / Persian / mixed / diacritic / fast / long / styled-ASS fixture costs the same as its
Latin control (e.g. 0.0138 vs 0.0167 ms per frame), with 2 log lines and no glyph search. Embedded tracks (MKV SubRip,
MKV ASS, MP4 mov_text) decoded by the console's FFmpeg 5.0 reach libass with identical text and millisecond timing.

Still not covered by any bundled font: CJK, Thai, Indic scripts, emoji, Urdu U+06C1 / U+06D2 - a box, as before, but
no log flood. A pathological subtitle event (one 20,000-letter word, a 100,000-character event) costs libass itself
140-250 ms per frame on a desktop CPU while it is on screen; bounding that needs a rebuilt libass.

## 2. Other findings and fixes

| # | Area | Finding | Severity | Fix |
|---|---|---|---|---|
| 1 | Log | warnings / errors bypassed the 16 MB cap: any flood could grow `log.txt` without end | Medium | hard cap 24 MB for everything |
| 2 | Playback / storage | `Mpv::stop()` (also run by every `Mpv::load`) wrote mpv's watch-later file: a synchronous write at every open, stop and channel change, one file per stream address kept for ever; never read (the app resumes from its own store) | Medium | not written any more |
| 3 | Privacy | `Mpv::load` logged the full stream address; mpv's "Playing: <url>" and FFmpeg's "Opening '<url>'" lines kept paths, where providers put tokens no rule recognises | Medium | addresses never logged by the loader; URLs in mpv / FFmpeg lines and in error details cut to their origin (`redact::urlsToOrigins`) |
| 4 | Privacy | the playlist address shown / logged as `host/…/<last segment>` showed a token used as the file name | Low | token-shaped names shown as "…" + extension |
| 5 | Network security | libcurl (PacBrew 7.80 has file, dict, gopher, ftp, imap, pop3, smtp, telnet, tftp, mqtt, rtsp, ldap, smb) was not restricted: an artwork address in a hostile playlist could read console files (`file:///data/PS4IPTV/profiles.json`) or send raw bytes to devices on the LAN (`gopher://`), also through redirects | High | API / playlist / artwork client and download transport: http and https only, also for redirects |
| 6 | Network security | redirects were followed blindly: https -> http for credential-bearing requests (Xtream API, playlists, downloads); a portal's MAC cookie followed a redirect to any host (libcurl 7.80 sends custom Cookie headers to other hosts) | Medium | every hop checked (`network/http_policy`): no https -> http for requests with credentials (clear message: enter http:// explicitly), portal requests stay on their host (www. or not), at most 8 hops; downloads that start on https stay on https |
| 7 | Network reliability | no retry at all: one connection reset, DNS hiccup or 502 / 503 / 504 failed a sign-in or catalog load | Medium | at most 2 retries, pauses 0.75 s / 2 s, only for quick temporary failures, never for timeouts, 4xx, TLS, too large, never after cancel or past half the time budget; the pause ends at once on cancel |
| 8 | Network | certificate failures, interrupted transfers and refused redirects were reported as generic errors | Low | own error kinds and messages (EN / TR) |
| 9 | Resource leak | each worker thread's curl handle was never freed when the thread ended | Low | released by a JobSystem worker-exit hook (a `thread_local` with a destructor cannot be used: no `__cxa_thread_atexit_impl` on the PS4) |
| 10 | UI freeze | Local Media listing ran `lstat` on every directory entry (thousands of pictures, entries past the cap) and read folders of any size, on the main thread | Medium | `d_type` first (no stat for skipped entries, `lstat` only when the type is unknown or for shown files' sizes), at most 50,000 entries read (flagged). 100,000-entry folder: 118 ms -> 10.5 ms on the desktop |
| 11 | Stutter during playback | every 15 s the player wrote favorites.json and history.json with `fsync` on the main thread | Medium | only changed files are written; the periodic save writes on a worker (snapshot on the main thread, generation-ordered writes, failed writes repeated); stop / pause / exit stay synchronous |
| 12 | Version | the version was written twice (APP_VERSION 0.3.0 and the PS4 APP_VER 00.30 by hand); `build_info.h` (commit shown in About / Diagnostics / log) was generated only when CMake configured, so a build after a commit showed a stale commit | Low | APP_VER derived from APP_VERSION (`cmake/app_version.cmake`, validated, tested); build info regenerated at every build; release check 13 compares param.sfo and the eboot with APP_VERSION |
| 13 | Navigation | "V7 IPTV" text next to the V7 symbol in Home's navigation | - | the symbol alone (product name kept on the welcome screen, About, PKG title) |

The version display: every in-app path prints `v` + APP_VERSION (`v0.3.0`); the only other representation is the
console metadata APP_VER / VERSION `00.30`. The next release is a one-line change (`set(APP_VERSION "0.4.0")` ->
APP_VER 00.40, which installs over 00.30).

Reviewed without a change needed: JSON nesting limit (64), numbers out of range (clamped), download file names from
the manifest (validated), Local Media traversal / symlinks / special files, certificate verification (never off,
packaged CA bundle), keyboard state parsing (fuzzed again), the libcurl / FFmpeg TLS path.
